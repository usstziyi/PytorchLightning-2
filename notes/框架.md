两者**没有继承关系，是平级的两套基类**，由 Trainer 当"导演"撮合它们合作。

## 各自职责

| | `LightningModule` | `LightningDataModule` |
|---|---|---|
| 定位 | 模型 + 训练逻辑 | 数据 + 加载逻辑 |
| 管什么 | 网络结构、`training_step`、`configure_optimizers` | `prepare_data`、`setup`、`train_dataloader` 等 |
| 继承自 | `torch.nn.Module`（本质是个模型） | 独立基类（只是数据容器） |
| 能不能独立用 | 可以，当普通 nn.Module 用 | 可以，手动调它的 dataloader |

所以它俩是**各管一摊的平级搭档**，不是父子/依赖关系。

## 怎么发生联系：通过 Trainer

```python
trainer = L.Trainer(...)
model = Classifier()           # LightningModule
dm    = ToyDataModule(...)     # LightningDataModule

trainer.fit(model, datamodule=dm)   # 一起交给 Trainer
```

数据流是这样串起来的：

```
dm.train_dataloader()  ──产出 batch──▶  model.training_step(batch)
      (LightningDataModule)               (LightningModule)
              ▲                                    │
              │           Trainer 调度             │
              └────────── 拿 loss 更新权重 ◀────────┘
```

即：**DataModule 负责"喂数据"，Module 负责"吃数据、算损失、更新参数"**，二者通过 batch 这一个接口解耦，谁也不 import 谁。

## 类比

- `LightningModule` = 厨师（会做菜：forward、算损失、调火候）
- `LightningDataModule` = 食材供应商（负责买菜洗菜：下载、切分、装盘）
- `Trainer` = 餐厅经理（把食材端给厨师，管节奏和流程）

换食材（换 DataModule）不换厨师，换厨师（换 Module）不用换食材，都是独立的。

## 一个细节

唯一"暧昧"的地方：`training_step` 里用的 `batch` 长什么样，取决于 DataModule 的 dataloader 产出什么。比如本文件里 DataModule 产的是 `(x, y)` 元组，[training_step](file:///Users/usst_ziyi/Programs/trae/DeepL/PytorchLightning-2/04_datamodule/toy_datamodule.py#L98-L99) 里就 `x, y = batch` 拆包——这算一种"软约定"，靠注释/文档同步，不是强约束。
